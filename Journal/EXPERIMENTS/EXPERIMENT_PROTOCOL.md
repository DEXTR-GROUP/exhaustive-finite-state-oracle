# EFSO — НОРМАТИВНЫЙ ПРОТОКОЛ ПРОВЕРКИ

**Статус:** КАНОНИЧЕСКИЙ

## 1. Назначение

Документ определяет минимальные требования к отдельной проверке, эксперименту или qualification run в EFSO.

## 2. Одна проверка — одна запись

Каждая самостоятельная проверяемая гипотеза, свойство или контрольная процедура получает отдельный идентификатор и отдельный документ результата.

## 3. Обязательные разделы результата

```text
1. ID / status
2. verification question
3. goal
4. finite-state construction
5. controls
6. metrics / equality policy
7. independent semantics
8. execution evidence
9. source commit
10. machine-readable artifact
11. result
12. interpretation
13. limitations
14. next decision
```

## 4. Определение пространства

Каждый run должен явно фиксировать:

- `space_id`;
- описание `F`;
- кардинальность `|F|`;
- способ enumeration;
- число реально обработанных состояний;
- причины исключения состояний, если исключения вообще предусмотрены формальной моделью.

Нельзя называть тест exhaustive, если фактическое покрытие не равно заявленной кардинальности.

## 5. Независимость

Результат не должен строиться на вызове IUT как собственного reference. Если сравнение выполняется с IUT, EFSO вычисляет ожидаемую семантику самостоятельно.

## 6. Controls

Должны быть предусмотрены проверки корректности самого harness, enumeration и формата evidence. Контроль oracle не может быть заменён единственным успешным сравнением с IUT.

## 7. Equality

Правило сравнения фиксируется до запуска. Для конечной точной арифметики применяется exact equality. Если применяется tolerance, указываются причина, значение и математическое основание.

## 8. Failure

При failure сохраняется:

```text
state
transition
expected
actual
first divergence, если определена
```

Если возможно, создаётся минимизированный witness.

## 9. Evidence

Минимальная цепочка:

```text
commit
+
protocol
+
run result
+
machine-readable evidence
```

## 10. Интерпретация

Результат не должен выходить за пределы проверенного пространства. `PASS` означает соответствие заданному критерию на заданном `F`, а не доказательство для всех возможных состояний системы.

## 11. Регрессия

Изменение модели, enumerator, transition engine или критериев сравнения требует повторной квалификации затронутых проверок.

## 12. Воспроизводимость

Другой запуск того же протокола с теми же входными данными и версиями должен позволять восстановить результат и evidence.

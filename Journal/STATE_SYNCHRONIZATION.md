# EFSO — СИНХРОНИЗАЦИЯ СОСТОЯНИЯ

**Статус:** НОРМАТИВНОЕ ДОПОЛНЕНИЕ  
**Назначение:** исключить расхождение между дорожной картой, реестром проверок, evidence и оперативным состоянием.

## 1. Иерархия источников

```text
REDMI.md
   ↓ задаёт нормативный порядок этапов
EXPERIMENTS.md
   ↓ фиксирует статус каждой проверки
CI / evidence
   ↓ подтверждает фактический результат
МАЯК.md
   ↓ фиксирует единственную ближайшую контрольную точку
CURRENT_STATE.md
   ↓ фиксирует подтверждённое состояние проекта
QUALIFICATION_NEXT.md
   ↓ фиксирует следующий обязательный этап
```

## 2. Правило статуса

Статус qualification case не может быть сильнее первичного evidence.

```text
PLANNED → RUNNING → PASS
                  ↘ FAIL
                  ↘ INCONCLUSIVE
```

`PASS` допускается только после фактического CI/evidence. После `PASS` запись в реестре закрывается до начала следующего этапа.

## 3. Правило перехода

После закрытия этапа выполняется атомарный документальный переход:

```text
CI / evidence
      ↓
EXPERIMENTS.md
      ↓
МАЯК.md
      ↓
CURRENT_STATE.md
      ↓
QUALIFICATION_NEXT.md
```

Следующий этап не должен начинаться при оставшемся `RUNNING` старого этапа в оперативных документах.

## 4. Роль дорожной карты

`REDMI.md` определяет архитектуру и порядок qualification stages:

```text
FM0–FM3
  ↓
E4–E12
  ↓
R4
  ↓
R5
  ↓
R6
  ↓
R7
  ↓
NumPy float64
```

Дорожная карта не является журналом текущих статусов. Фактический статус определяется `EXPERIMENTS.md` и evidence.

## 5. Текущая контрольная точка

На момент фиксации этого документа:

```text
FM2-R6-001 = PASS
R6-NUM-001 = PASS
R7-NUM-001 = NEXT
```

Следующая реализация обязана начинаться с `R7-NUM-001` и не должна возвращать R5/R6 в состояние `RUNNING` без отдельного нового qualification case.

## 6. CI guard

`validation/state_sync_check.py` проверяет текущую синхронизацию четырёх оперативных документов перед qualification execution.

Нарушение синхронизации должно останавливать CI, а не маскироваться успешным вычислительным тестом.
